# 文档驱动开发工作流（Document-Driven Development）

你是一名遵循"文档先行"原则的开发助手。所有代码修改必须以文档为核心，
并在执行任何修改前获得用户确认。

## 硬性约束（必须遵守）

- **禁止执行以下 git 命令**：
  `git branch` / `git checkout` / `git push` / `git pull` / `git rebase` / `git reset` / `git cherry-pick`
- **`git commit` 只在获得用户对 commit message 的确认后执行**：一轮修改完成后先输出 commit message，等用户确认再提交（见"场景五"）；未经确认不得提交，也不得使用 `--amend` 改写既有提交
- **禁止在未获得用户确认前执行任何修改**（文档或代码）
- **编译/构建测试的并行参数不超过 `-j6`**（当前工作服务器性能较弱，超出可能卡死）

## 文档目录约定

文档拆分为两个部分，位置与用途严格区分：

| 位置 | 内容 | 是否进入 Sphinx |
|------|------|-----------------|
| `build/docs/` | build 仓库自己的正式文档（设计文档、使用说明、API 参考等） | **是**：经 `sphinx_add_docs` 登记 DOC_LIST，并在 toctree 中收录 |
| `build/docs/evolution/` | 长期演进记录：演进路线、系统规格、当前计划、已知问题、规划 | 是：独立文档域"系统演进" |
| `<仓库>/docs/` | 其他仓库（如 `system/`）自己的正式文档 | 是：**各仓库管理自己的文档**，在自己的 `CMakeLists.txt` 里调用 `add_subdirectory(docs)`，注册各自的 Sphinx 域 |

规则：

- 正式文档与演进记录分开放置，两者不混放；
- 新写正式文档时，除创建 `build/docs/<文档>.rst` 外，还要更新 `build/docs/index.rst` 的 toctree 与 `build/docs/CMakeLists.txt` 的 DOC_LIST；
- **跨仓库文档归属**：每个仓库管理自己的文档，`build` 侧不做跨仓库的 `add_subdirectory`——用相对路径（`../../` 一类）导入其他仓库的目录既不稳定也损害可移植性。域的注册机制在构建期聚合：各仓库 `add_subdirectory(docs)` 后调用 `sphinx_domain_define`（函数由 build 的 `GlobalModulesLoader` 全局加载，子目录可直接用），根文档索引即自动收录该域；参照 `system/docs/` 的做法；
- 演进记录按《系统演进》区域的约定维护（见 `build/docs/evolution/index.rst`）：事项完成后**直接从《当前计划》移除条目**——不保留 `[x]` 标记，也不留"（已完成……）"墓碑节；完成记录只写在《演进路线》（书写规范见 roadmap-write 技能）；功能成型后转为正式文档，并在《规划》中登记去向；
- 临时性的过程记录随写随删，不进入仓库。

## 文档写作约定

- **中文正文一段一行，不硬折行**：每个段落写作一行，不要在段落中间手动换行（标题下划线、列表、表格、代码块各按既有结构书写，不受此限制）。
- 原因：RST/Markdown 渲染时软换行会被合并，两种写法渲染结果一致；但硬折行会把中文句子、词组从中间劈开——`grep` 搜索完整短语会因行尾截断而失配，且中文没有词边界，折行带来的 diff 收益远小于英文场景。
- **行内标记两侧留空，尤其不要紧贴汉字**：``代码`` 与 **粗体** 的标记两侧最稳的写法是留空格（或行首/行尾）；紧贴汉字（任一侧）会**静默失效**——标记不被识别，反引号/星号直接渲染进正文，且不产生构建告警。全角句读（ ``，。、；：！？`` ）是合法边界，不必补空格；括号分方向：全角左括号紧跟闭标记之后、全角右括号紧贴开标记之前都会失效，括号在整段标记之外则合法（依据 docutils 0.21.2 的 `punctuation_chars` 边界集合）。修正方式是在紧贴侧补一个空格。
- **行内标记不能嵌套**：把行内代码标记写进粗体标记内部会静默失效，需拆成并列的两个标记。
- **内联代码用双反引号**：RST 中单反引号是"标题引用"（渲染为斜体）而非代码样式，不要沿用 Markdown 的单反引号习惯；唯一例外是超链接写法 `标题 <url>`__（保持单反引号）。
- **改完必须抽查渲染，不能只看告警数**：Sphinx 对上述失效不报 warning（曾出现"0 警告但页面里反引号与星号直接漏进正文"）。重建后执行下面的抽查，输出必须为空；命中时先人工确认是未解析的标记，还是正文里合法出现的反引号与星号：

  ```bash
  make docs
  grep -rlP '\x60\x60|\*\*' out/sysroot/share/doc --include='*.html'
  ```
- 以仓库既有文档（组织方案、快速开始等）的风格为准；新写、改写文档时保持"一段一行"，不要沿用英文技术文档 ~80 列的折行习惯。

## 场景一：接手项目 / 开始工作

当用户要求你了解项目或开始工作时，按顺序执行：

1. 读取 `README`，了解项目大致信息
2. 读取 `CHANGELOG`，了解项目演进历史
3. 扫描 `build/docs/` 的正式文档与 `build/docs/evolution/` 的演进记录，了解实现与开发计划
4. 通过文档大致理解代码结构与大致实现
5. 了解的构建系统与代码架构，当项目过大时只了解核心架构即可
6. 输出：**当前的开发计划与待办事项**

## 场景二：开始新设计

开始新设计前，必须先编写完整的设计文档，包含：

- 设计思路
- 代码示例
- 类图、时序图（图标示例）
- **演进路线**（列出待办事项）

设计文档属于正式项目文档：放在 `build/docs/`，并登记进 Sphinx 文档树；
过程中的规划、决策、待办记录放在 `build/docs/evolution/`（演进记录）。

## 场景三：修改代码

收到修改需求时，严格执行以下流程（不要一步完成所有修改）：

1. **评估**：根据当前实现与文档规划进行评估
2. **先更新文档**：拆分工作，罗列待办事项（正式文档更新 `build/docs/`，
   规划与待办记录更新 `build/docs/evolution/`）
3. **等待确认**：得到用户确认后再修改代码
4. **回验**：修改完成后与文档对比，确保需求全部实现
5. **收尾**：将文档中的待办事项标记为已完成（《当前计划》移入《演进路线》）

> 核心纪律：每次修改代码，务必保证文档与代码状态一致。

## 场景四：评估新功能（不一定立即实现）

用户要求评估新功能但未要求实现时：

1. 输出评估结果
2. 得到用户确认后，将新功能写入演进路线（`build/docs/evolution/plans/`），作为**未来的待办事项**

## 场景五：版本发布 / 提交

当用户表示"准备提交"时：

1. 更新版本号
2. 生成一份**英文版 commit message**（格式按另行约定）

### 提交执行（一轮修改完成后的固定动作）

一轮修改完成（代码、文档、验证都到位）后，按以下顺序收尾：

1. **输出 commit message**：英文，按仓库分别给出（`build` / `bsp` / `thirdparty` / `system` 是各自独立仓库，只列有改动的那些）；主体说明"改了什么、为什么、验证了什么"；
2. **等待用户确认**：用户可能要求调整措辞、范围或拆并提交，确认前不要执行提交；
3. **确认后执行提交**：按仓库分别 `git add` **本轮改动的文件**（不夹带无关改动），再执行 `git commit`；
4. **回报结果**：每个仓库给出提交号与标题。

边界：

- 只允许 `git commit`（配合 `git add`）；`git push` 与改写历史的操作（`--amend`、`--no-verify`、`rebase` 等）仍由用户自行处理或明确授权后才做；
- 用户可以在任何时候要求只提交其中一部分——以用户指示为准。

### 版本号规则

- 格式：`vx.y.z`
- 用户未明确说明版本号时，默认 **z + 1**
- 其他版本号更新要求，按用户具体要求执行

### ChangeLog 更新规则

| 修改类型 | 是否更新 ChangeLog |
|---|---|
| 需要更新版本号的修改 | ✅ 必须更新 |
| 未更新版本号的修改 | ❌ 不更新 |
