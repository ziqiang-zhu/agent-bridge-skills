# 组件文档三件套（设计 / 开发 / 使用）

一个有成规模使用方的组件，文档按受众拆成三份——**设计文档、开发文档、使用文档**。三份的受众、内容、边界互不相同：写之前先分清"这段话是给谁看的"，避免同一内容重复出现在多份里（重复必然腐化失同步）。

## 三份的分工

| 分册 | 受众 | 回答的问题 | 核心内容 |
|---|---|---|---|
| 设计文档（`-design`） | 设计者、评审者 | **为什么这样设计** | 设计思路与架构、需求蓝图（含草图布局）、关键决策与取舍（含被否掉的方案）、接口形状草案、实现路线与实施状态表、演进锚点 |
| 开发文档（`-development`） | 开发者（使用与扩展组件的人） | **怎么用、怎么扩展** | 产物清单（装了什么、在哪、什么形态）、快速上手、API 说明（接口表 + 代码示例）、示例链接、扩展指南（加组件/换策略/调清单的具体做法与位置）、边界与注意事项 |
| 使用文档（`-user`） | 开发者与最终用户 | **怎么操作、日常怎么用** | 界面/行为说明、常用命令（构建/部署/验证/自查）、常见任务的思路指引、注意事项（交互禁区、已知怪癖） |

内容分界的三条判据：

- **"为什么"进设计，"怎么做"进开发，"做什么"进使用**——设计理由出现在开发文档里、操作步骤出现在设计文档里，都是分册越界；
- 组件的 **API 契约归开发文档**；API 的 **设计动机归设计文档**——同一接口两处各说一面，用交叉引用（书名号指向对方分册）衔接，不复制内容；
- **一次性内容**（排查过程、临时方案）不入正式分册——进《已知问题》或《演进路线》。

## 命名、位置与注册

沿用 Launcher 文档集（`system/launcher/docs/`）确立的范例：

```
<组件源码目录>/docs/
├── index.rst                    组入口（组名标题 + toctree 三份）
├── <组件名>-design.rst
├── <组件名>-development.rst
└── <组件名>-user.rst
```

- sphinx 注册：组件 **自管文档**——组件 `CMakeLists.txt` 里 `add_subdirectory(docs)`，`docs/CMakeLists.txt` 内 `sphinx_add_docs(<组id> DOMAIN <域> DOC_LIST ...)`（分散注册；域在顶层统一定义，如 system 域定义在 `system/CMakeLists.txt`）；组 id 全局唯一；
- 命名后缀固定 `-design`/`-development`/`-user`；标题行的等号/横线宽度 ≥ 标题显示宽度（中文按 2 列计）；
- 交叉引用用书名号文本（《XXX》）而非 Sphinx 引用，除非确需跳转。

## 与实现同步

- **文档先行**：设计文档先写、确认后实现；开发/使用文档随实现落地逐步充实（未落地的小节显式标注"规划中"并说明现状）；
- **实施状态表**：设计文档维护一张"项 / 状态 / 说明"表，随实现滚动更新——它是三份中唯一追踪"做到哪了"的地方；
- 行为变化时检查三份是否都受影响（例：chrome 层序变化同时影响设计分册的层序描述、开发文档的边界、使用文档的注意事项）。

## 单页与全套的取舍

不是所有组件都需要三件套。判断标准：

- **有成规模使用方、有多类受众**（如框架库、桌面、平台服务）→ 三件套；
- **小型工具、单一用途**（如 screenshot 排障工具）→ 单页即可，页内可按"用途/用法/边界"分节；
- 介于两者之间时先单页，内容增长到单页超过约 150 行、且能清晰拆出两类以上受众时再拆三件套。

## 写作基调

- 正式文档的严肃性：不记录排查过程、不写临时方案、不用口语；
- RST 排版边界：`**`/`` `` `` 定界符不紧贴中文；标题线宽度足额；全角括号不紧跟闭定界符；
- 每份开头一段定位说明（本册面向谁、覆盖什么、其余见哪份），读者一眼知道该读哪本。

## 范例

`system/launcher/docs/`——Launcher 文档集是本规范的现行范例（设计含草图布局与实施状态表、开发含模块结构与扩展指南、使用含行为与注意事项）。
