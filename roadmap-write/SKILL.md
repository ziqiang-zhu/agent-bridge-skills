# roadmap-write：演进路线（CHANGELOG）条目书写规范

目标文件：`build/docs/evolution/roadmap.rst`（build 仓库）。

本技能只规范 roadmap 的**写法**与**更新时机**。RST 排版边界、交付前机械自查与渲染抽查等通用文档规则见 document-driven-development 技能的「文档写作约定」，此处不重复。

定位先分清：演进路线是 **CHANGELOG**，按时间倒序记录已完成并验证过的事项。它不是参考文档——历史条目可能过时，不要把它当作现状依据；反过来，新条目里引用的组件名、符号名、命令必须与**当前代码**一致。

## 更新时机（硬性）

- 一轮修改**完成并验证后当轮写入**，与《当前计划》的条目移除同步进行——不攒批、不等提交轮、不以用户未提"记录"为由跳过；
- 完成记录只写在《演进路线》：《当前计划》里的条目直接移除，不留 `[x]` 标记、不留"（已完成……）"墓碑节（与 document-driven-development 的演进记录约定一致）。

## 倒序规则（硬性）

- **第一条总是最近的修改**，整个文件从上到下时间严格递减；
- 新的一天：新建日期节，插在文件头部引言之后、现有最新日期节之前；
- 同一天补条目：插在该日期节的**第一条**位置（节内同样倒序），不要按锚点插到中间或尾部。

日期节结构（下划线恰好 10 个 `-`，日期用宿主当天日期）：

```rst
2026-09-19
----------

- **领域**：条目内容；
```

## 条目格式

```rst
- **领域**：主题——展开与根因；验证：实测数据；
```

- **领域词加粗 + 全角冒号**。领域词参照文件中既有条目选取（常用：构建系统、BSP、平台、修复、验证、文档、系统 init、第三方、测量），确实没有合适的才自拟一个同样简短的；
- 内容三要素：**改了什么 / 为什么（动机或根因）/ 验证数据**。没有实测的不要写"验证"；
- 路径、命令、符号名、组件名一律用行内字面量 `` `` ``；主题与展开用 `——` 衔接，并列要点用 `；` 分隔；
- 勾销《当前计划》待办时在条目里注明"（勾销《当前计划》同名待办）"；连带改了其他文档时注明（如"《快速开始》同步改写"）；
- 条目可以长，但一条只讲一件事；同类小修合并为一条，不要碎片化。

## 完成后检查

1. 重建文档站：`make MAKE=/usr/bin/make CMAKE="snap run cmake" docs`，Sphinx 告警须为 0；
2. 泄漏扫描按 document-driven-development「文档写作约定」的渲染抽查执行——剥标签后 `**` 与反引号字面量的计数都必须为 0，只扫 `**` 会放过行内字面量泄漏。

## 示例

合格条目（领域加粗、三要素齐全、行内字面量、边界合法）：

```rst
- **构建系统**：阶段一配方顺序修正—— ``$(SYSROOT_MARKER)`` 改为先 ``--install --component sysroot`` （prebuilt 内容落构建 sysroot）、再 ``--build sysroot-group`` 。原顺序颠倒：glibc 切到 prebuilt 后没有构建步骤，libc 只能靠 component install 落位，源码包 configure 时 ``--sysroot`` 里没有 libc，报 ``C compiler cannot create executables`` ；全源码配置下该缺陷潜伏不显。验证： ``make config`` 全链通过，util-linux configure 在原失败点通过；
```

不合格示例（定界符紧贴汉字，`**` 会原样泄漏到 HTML）：

```rst
- 构建系统：阶段一配方顺序修正——**先装 prebuilt**再构建；   ← 「再」紧贴闭定界符，非法
```
